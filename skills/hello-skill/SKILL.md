# Hello Skill

请原样输出这一行：

**HELLO from ~/.dsh/skills/hello-skill/SKILL.md**

然后用一句话说明：这句话不在你的训练数据里，是刚才通过 `skill` 工具从本地磁盘上的一个 Markdown 文件读到的。

如果用户问「这是怎么做到的」，按下面的顺序讲，一次讲一层，不要一口气倒完。

## 第一层：它只是一个文件

```
~/.dsh/skills/hello-skill/SKILL.md
```

没有编译，没有注册表，没有 npm 包。DSH 扫描几个约定目录，把找到的每个 `SKILL.md` 的 frontmatter 解析出来，组成一份目录给模型看。

模型最初**只看到目录**（`name` 和 `description`），正文要等它决定加载之后才会被读进来。这就是为什么 `description` 比正文更重要：它是触发条件。

## 第二层：生命周期

这三步用户可以自己跑一遍，全程不用重启 DSH：

```sh
# 1) 删掉它，问模型有没有这个技能 → 回答「没有」
rm -rf ~/.dsh/skills/hello-skill

# 2) 放回来，再问一次 → 回答「有」，并能加载
mkdir -p ~/.dsh/skills/hello-skill
# （把 SKILL.md 写回去）

# 3) 改一个字，再加载 → 立刻拿到新内容
```

关键在于**中间没有任何重启动作**。文件出现，技能就在；文件消失，技能就不在。

## 第三层：这背后是什么

DSH 建立在 Cordis 之上，Cordis 有一篇论文叫《A Programming Paradigm for Spatiotemporal Composability》。技能的这个行为，正是论文形式化的那套东西的最小可观察实例。

论文把动态组合拆成两个维度：

**时间可组合性（temporal composability）** —— 组件被移除时，它对环境的修改被完整撤销。论文的做法是让每个作用都携带它的逆操作，运行时追踪，卸载时按 LIFO 顺序恢复（§3.1 可逆效应）。

对应到技能上：删掉目录，那个技能就从模型的目录里干净消失，不留残留。

**空间可组合性（spatial composability）** —— 组件声明它依赖什么，运行时在依赖出现、消失、或换了提供者时重新判断它能不能运行（§3.2 反应式 coeffect）。

对应到技能上：`skill-filesystem` 这个提供方声明它提供 `skills` 能力，`tool-skill` 声明它需要 `skills`。前者不在，后者就不激活。

论文里的组件生命周期只有两个状态（§4.1，图 1）：

```
Inactive  ⇄  Active
        L-Reload / L-Unload
```

驱动这两个转换的是一次比较：**当前生效的视图（committed view）和目标视图（target view）是否一致**。不一致就发起转换。上面那三步演示，就是这个比较在文件系统层面的表现。

论文把一个组件的实例叫 **fiber**（§4.1，Definition 44），它记录了：来自哪个组件、父 fiber 是谁、自己提供了什么、当前处于生命周期的哪一步。这也是为什么同一个组件可以被实例化多次而互不干扰。

**不需要读论文也能用技能。** 但知道这套机制之后，两件事会变得可预期：为什么改完文件不用重启，以及为什么某个技能"明明在那儿却不生效"（多半是依赖没满足，或者 frontmatter 被 fail-closed 丢弃了）。

## 第四层：接下来做什么

- 想自己写一个：看 `dsh-skill-dev` 技能
- 技能不出现、排查不出原因：看 `dsh-troubleshoot`
- 想做插件（技能做不到的事）：看 `dsh-first-plugin`

## 讲解时不要做的事

- 不要一次把四层全倒出来，用户问到哪层讲哪层
- 不要在用户只想跑通时讲论文
- 不要把论文的形式化符号搬进来，讲行为就够了
- 不要说「技能就是提示词」，它有生命周期、有优先级、有依赖，提示词没有
